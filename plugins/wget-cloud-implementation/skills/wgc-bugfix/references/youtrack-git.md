# Git для задач YouTrack

Применяется при YouTrack work item и имеет приоритет над общими примерами веток. Планирование/создание карточек само по себе не создаёт ветки и коммиты.

| Work item | Base | Branch | Merge target |
|---|---|---|---|
| Самостоятельная задача | dev | `<prefix>/<ISSUE-ID>` | dev |
| Эпик | dev | `epic/<EPIC-ID>` | dev |
| Задача эпика | epic/<EPIC-ID> | `<prefix>/<ISSUE-ID>` | epic/<EPIC-ID> |

Проверяй существование dev и remote tracking в каждом repository. Не подменяй отсутствующий dev веткой main/develop; это blocker. Для эпика создавай отдельную одноимённую epic-ветку в каждом затронутом repository. Задача нескольких repositories имеет отдельную task-ветку в каждом. Подзадачи эпика тоже ответвляются от epic, а не от ветки родительской задачи; зависимые изменения сначала интегрируются в epic.

Type Bug/Баг → `fix`; Research/Исследование → `research`; Epic/Эпик → `epic`. Для Task/Subtask prefix по категории: Функциональность → `feat`, Рефакторинг → `refactor`, Тестирование → `test`, Документация → `docs`, Инфраструктура/Технический долг → `chore`. Type Bug/Research имеет приоритет над категорией. Пустая/неизвестная категория → выяснить nature of change при планировании, не угадывать по одному заголовку.

Каждый commit message: `[ISSUE-ID]: Название задачи`, например `[BE-4]: Оплата картой через YooCassa`. Без `feat:`, `refactor:`, `test:`, суффиксов инструментов и рекламных приписок. Используй фактический ID и согласованное название карточки; пример BE-4 не основание создавать такую карточку. ID/branch проверяй как данные, не интерполируй issue title в shell code. Для сообщений используй файл/structured argument.

## Выполнение и squash

1. Исследуй существующие ветки, uncommitted changes, worktrees, submodules и remote heads. Не reset/clean/stash чужие изменения. Существующая task/epic branch требует проверки происхождения и уже выполненной работы; не пересоздавай её принудительно. Создай изолированный worktree, если нужно избежать collision.
2. `BranchPlan`: repository, issue ID, type/category, base/target, base SHA, task head, epic head, ownership и permissions. Применяй после readiness; при начале работы Stage=В работе через MCP. Не начинай write slice, если обязательный transition не подтверждён.
3. Перед task→epic все коммиты самой task-ветки squash в ОДИН коммит задачи. Сохрани tree equivalence исходному проверенному task diff, не включай коммиты основания или другой задачи. Просто `merge --squash` при сохранении многокоммитной task-ветки не выполняет требование пользователя.
4. Не переписывай общую опубликованную ветку без явного разрешения её rewrite. Если понадобится force push — остановись до него; никогда не обходи destructive Git hooks. Сначала подготовь точные old/new heads и план; применяй только разрешённый безопасный способ. Локальная private-ветка также должна сохранять чужие изменения.
5. После squash проверь один task commit относительно актуального base, точное сообщение и итоговый tree/diff. При изменении base или разрешении конфликтов проведи релевантные проверки итоговой интеграции. Rebase не переносит автоматически evidence на изменённый tree.
6. Интегрируй в актуальную epic-ветку без дополнительного merge-коммита там, где possible fast-forward; затем следующая зависимая task branch берётся от обновлённого epic head. Не стирай чужие commits. Epic→dev сохраняет отдельные task commits, весь эпик в один коммит не squash. Самостоятельная задача сливается только в dev.

Commit/push/PR/merge/release/deployment выполняются в пределах явного разрешения текущей сессии; правило формата не является разрешением публикации. Не переспрашивай уже данное разрешение того же scope. Git merge не является dev/production delivery; production rollout требует отдельного точного GitOps approval.
