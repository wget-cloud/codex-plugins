# Жизненный цикл эпика YouTrack

Обязателен при создании, доработке и реализации эпика, а также при работе с отдельной задачей, входящей в эпик. Это стадийный процесс, а не создание сразу готового backlog за один ответ. Продолжай с фактической Stage существующей карточки; не пересоздавай эпик и не проигрывай задним числом уже пройденные стадии. Указание «создай эпик» разрешает раннюю карточку, но не заменяет approvals следующих этапов.

## Ответственность

Project Manager владеет состоянием эпика, полным составом, переходами и их доказательствами. Product Manager ведёт совместную с пользователем продуктовую проработку; исследователи проверяют код и варианты; Architect и Effort Estimator подключаются к нужному этапу. Только YouTrack Operator выполняет записи через MCP по проверенному `EpicStagePlan`. Orchestrator независимо сверяет реальные основания, явные решения пользователя и результат записи. Project Manager не утверждает продуктовые решения за пользователя.

## Стадии и условия

| Переход | Работа и условие перехода |
|---|---|
| Backlog → Исследование | Создать ранний эпик PRD с целью, текущими фактами и открытыми вопросами; при начале совместного исследования перевести его в Исследование. Полная декомпозиция и оценки будущих задач ещё не требуются. |
| Исследование → Груминг | Совместное исследование с пользователем: интервью, код, альтернативы, ограничения и результаты Research. Эпик описан, все существенные вопросы по нему закрыты, нет нерешённых проблем. **Только явный approval пользователя на переход к Грумингу** для актуального scope. |
| Груминг → Исследование | В обсуждении подготовленного эпика выявлены неточности, неизвестные или проблемы реализации, требующие исследования. Записать причины, возобновить исследование; прежний approval выхода из исследования не переносится на изменённый scope. |
| Груминг → К реализации | Обсуждены все тонкости, сценарии, альтернативы, AC, риски и реализуемость. Пользователь принял решение о готовности эпика по результатам груминга. Решение фиксируется как `grooming_passed`; PM не принимает его молча. |
| К реализации → Декомпозиция | Начата разработка подробного состава задач по прошедшему груминг эпику. PM переводит Stage до публикации задач разработки. |
| Декомпозиция → Груминг | При детализации найдены вопросы или проблемы, влияющие на эпик. Сохранить созданные задачи и причины возврата, пометить незавершённую подготовку в описаниях; не удалять и не дублировать карточки. После груминга вернуться через К реализации к Декомпозиции. |
| Декомпозиция → Готово к разработке | Все задачи разработки созданы в нужных проектах со Stage=К выполнению, корректно связаны с эпиком, описаны с нюансами, отдельными планами, AC, зависимостями, SP и проверками. У каждой доказана готовность, нет вопросов/пробелов/циклов. **Только явный approval пользователя на готовность к разработке** по полному актуальному составу. |
| Готово к разработке → В разработке | Хотя бы одна **задача разработки** действительно взята в работу и её переход в В работе подтверждён через MCP. Затем PM немедленно инициирует переход родительского эпика. Research сам по себе не запускает разработку эпика. |
| В разработке → Готово к выпуску | Все задачи разработки выполнены и находятся **в точном статусе Готово к релизу**. Проверяется весь состав, не последняя партия или один репозиторий. |
| Готово к выпуску → Приёмка | Все задачи разработки находятся **в точном статусе На production**, выкладка подтверждена. Название Stage берётся из схемы: `Приёмка`, с «ё». |
| Приёмка → Реализован | Пользователь проверил на production все задачи разработки и явно принял результат эпика. Автоматическое QA или verdict Product Manager этого не заменяют. Задачи могут быть На production или уже Закрыто после подтверждённой пользовательской приёмки. |

Не пропускай этапы и не продвигай эпик при смешанных неподходящих статусах. Более поздний статус одной задачи не заменяет точное условие для всего состава. Если существующий эпик оказался вне последовательности, PM описывает расхождение и предлагает пользователю корректировку; не откатывает доставленные задачи искусственно ради таблицы. Отложен/Отменён, изменение состава и нестандартное возобновление требуют отдельного решения пользователя; этот контракт не выполняет их автоматически.

## Исследование, состав и готовность

На Исследовании допустимо создавать связанные задачи Type=Research с конкретным вопросом, ожидаемым выводом, границами и SP собственной исследовательской работы. Это исключение из запрета публиковать неподготовленные задачи разработки. Ранний эпик не объявляется полностью оценённым или готовым к разработке. Исследования могут исполняться, пока эпик находится на Исследовании; обычная проверка readiness родительского эпика для development к ним неприменима. Результаты исследований должны быть включены в описание эпика и рассмотрены пользователем до Груминга.

Раздели полный EpicInventory на development, research и явно cancelled. В development входят все включённые в поставку Task/Subtask/Bug и другая фактическая работа по изменению продукта, независимо от проекта или способа связи. Не считай все связанные карточки членами автоматически. Завершённые Research исключаются из проверки релизных Stage; незавершённые значимые исследования блокируют дальнейшее продвижение. Явно отменённые пользователем задачи исключаются только после согласованного изменения scope и подтверждённого статуса Отменено. Внешние зависимости сверяются отдельно и не исчезают из планирования. Пустой development inventory не удовлетворяет условиям готовности/релиза по принципу «все ноль задач готовы».

На Декомпозиции исследуй и опиши КАЖДУЮ задачу, включая вложенные и межпроектные работы. Не выдавай одну общую оценку эпика вместо SP задач; не удваивай объём родителей и подзадач. Partial publication не означает завершённую декомпозицию. Возврат на Груминг допустим до завершения inventory, если вопрос возник в процессе его подготовки; сохраняй известные IDs и явно отмечай неполноту. Возобновляй по созданным IDs и перечитывай карточки, а не создавай копии. Не начинай реализацию до подтверждённой Stage=Готово к разработке и readiness конкретной задачи.

## Переход через агентов и MCP

1. PM перечитывает эпик, комментарии/решения, актуальную schema, весь состав с пагинацией, статусы и зависимости; формирует `EpicStagePlan` с ожидаемым исходным состоянием и scope revision. Scope revision — SHA-256 канонического snapshot требований, AC, состава, релевантных доказательств и предметных решений, без самих approval markers и их ревизий; не только Git revision.
2. Orchestrator сопоставляет найденные вопросы, evidence и approval с реальными данными и историей общения. Разрешение имеет scope, исходную/целевую Stage и revision. «Продолжай», «создай» и старый approval нельзя использовать как согласие на ещё не предъявленный переход. Уже данное точное решение повторно не запрашивается.
3. При открытых вопросах/отсутствующем approval PM выдаёт `awaiting_user`, задаётся конкретный вопрос с подготовленным результатом и условиями перехода. **Stage не меняется; задача разговора может завершить ход в ожидании пользователя. Это пауза, а не завершение эпика.** Независимое разрешённое исследование продолжается.
4. PM с `stage_ready` передаёт план Operator. Operator проверяет условия, перечитывает ожидаемое состояние непосредственно перед записью, меняет только разрешённые поля и повторно читает результат. Если snapshot устарел — новый план; семантическое изменение инвалидирует прежний approval. Чужие тексты и blocker fields сохраняются.
5. Только подтверждённый переход получает `synced`/`no_changes`; при записи используются существующие MCP инструменты, серверный workflow этим плагином не устанавливается. Ошибка записи не запускает следующий этап. Для случая «уже применено» подтверждается целевая Stage и тот же scope/план, а не придумывается переход from=to.
6. Вызывай PM при завершении текущего этапа, изменении требований/состава и после подтверждённого изменения Stage любой задачи разработки: в скиле эпика **и** в standalone implementation/bugfix дочерней задачи. После перехода первой задачи в работу синхронизируй эпик до продолжения write slice. Сбой родительского перехода — явный blocker, не повод утверждать, что синхронизация завершена.

Плагин проверяет и двигает Stage во время работы агентов. Он не является фоновым наблюдателем за ручными изменениями вне сессии. При следующем запуске выполняется reconciliation с текущим состоянием.

## Машинный контракт

PM: `role=project-manager`, `phase=lifecycle`, verdict `stage_ready | awaiting_user | stage_blocked`; `input_revision` и `assessment_revision` как у обычного назначения. Дополнительно `epic_stage_plan`. Эти verdicts не закрывают старые project/scope/reconcile gates. В остальных phase сохраняются прежние verdicts. Operator возвращает тот же план с обычным verdict и пустой phase после записи; его stage sync требует matching current PM plan.

`epic_stage_plan` содержит **ровно** поля:

- `epic_id`, `scope_revision` (SHA-256), `from_stage`, `to_stage`;
- boolean `inventory_complete`, `epic_described`, `questions_resolved`, `grooming_complete`, `decomposition_complete`, `blocking_findings`;
- `evidence_refs`: 1–20 opaque handles;
- `tasks`: полный состав до 10000 записей `{id,kind,stage,ready,completed,production_verified,user_accepted,evidence_ref,exclusion_decision_ref}`. Kind: development/research/cancelled, четыре факта — boolean. Для cancelled обязателен handle решения и Stage=Отменено; для остальных exclusion_decision_ref пустой;
- `approvals`: до четырёх `{kind,scope_revision,decision_ref}`, где kind — research_to_grooming/grooming_passed/development_ready/production_accepted. Revision совпадает с планом, kind уникален.

Handles — 1–200 ASCII символов из букв, цифр, `_ . : / -`, без raw prompts, имён пользователей, текстов карточек или токенов. IDs уникальны. Scope revision/handles — утверждения агента; hook проверяет структуру, разрешённый переход и условия, но **не доказывает происхождение approval или реальность MCP-данных**. Их независимо сверяет Orchestrator. Внутри hooks нарушение контракта не засчитывается как успешный переход. Если полный epic_inventory уже записан, переход вперёд должен включать тот же полный набор IDs; последняя партия его не заменяет. Прямой MCP write без marker этим механизмом не перехватывается: Operator обязан применить проверку до записи.
