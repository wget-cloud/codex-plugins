# Проверки без дублирования

При `MVP_SKIP_TESTS: true` из `SKILL.md` исключи из `CheckPlan` и всех T0–T3 любые тестовые команды (включая существующие, race test и smoke tests), создание/изменение тестов и расчёт/проверку покрытия. Выполняй применимые build, vet, lint, Buf, static/contract checks. Отметь test/coverage gates репозитория и CI как невыполненные, а не успешные. При `false` действует обычный порядок ниже.

Один назначенный владелец выполняет проверку; остальные используют актуальный результат, оценивая его достаточность. Reviewer проверяет смысл assertions и diff, QA — поведение; никто не повторяет всю suite коллеги автоматически. Применяй ступени T0–T3 и cache/invalidation rules из [coordination contract](coordination-efficiency.md).

До write составь компактный `CheckPlan`. Implementor выполняет targeted T0 и один affected-scope T1. T2 выполняется один раз на service/release boundary только по repository requirement или явному запросу; T3 — только в пользовательском delivery scope.

Повтор требуется после релевантного изменения, failed run, изменения окружения/зависимости или нового риска. Факт запуска до изменения не доказывает текущее состояние. При неясной области влияния проверка повторяется. Проверки AGENTS.md/CI обязательны; шаблонный список плагина — подсказка для поиска настоящих требований, не дополнительный universal CI floor.

В task-local ledger сохраняй только метаданные: hash/id команды, revision, environment fingerprint, scoped paths, owner и successful flag. Окружение здесь означает контекст запуска; реальную версию сервиса/данных/зависимостей проверяет владелец evidence. Не сохраняй raw commands/output. Ошибка повторной проверки отменяет прежний успех. Source/lock/config change отменяет относящиеся к нему результаты; при неизвестной зависимости не переиспользуй прошлое evidence.

Новый тест нужен для критичного invariant, воспроизводимого дефекта или основного happy path без покрытия. Порядок: existing test → update → добавить минимальные 2–5 cases → none при низкой regression value. Сначала реализуй связный fix, тесты пиши вместе с кодом; не проектируй исчерпывающий suite заранее и не повышай coverage сверх repository gate.

Отчёт короткий: результат, changed scope, проверки и evidence, blockers. Не пересказывать историю задания. Передача finding: scenario → evidence → impact → required behavior. Не объявлять отсутствие дефектов гарантией безошибочности. Token usage измерять только из доступной фактической телеметрии; размер контекста и число запусков — отдельные proxy, не выдуманные токены.
