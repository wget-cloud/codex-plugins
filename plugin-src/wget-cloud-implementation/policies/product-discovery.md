# Продуктовая проработка задач

Обязательна во всех четырёх процессах до создания карточек или реализации. Глубина зависит от неизвестности; для эпика исследуй весь результат и каждую составляющую задачу до первой write wave. Запрос на план не означает запуск реализации.

## Исследование и интервью

1. Product Manager (при создании), либо Orchestrator (при реализации), выясняет проблему, пользователей, текущий процесс, измеримый результат и границы. Сначала используй уже полученные ответы.
2. Implementation Auditor/Explorer проверяет AGENTS.md, документацию, source → API/consumer → runtime evidence, существующие карточки и дубли. Название проекта не доказывает соответствие одному репозиторию. Зафиксируй repository/remote/owner/base SHA для каждой области; отсутствующий доступ обозначь пробелом, не выдумывай выводы.
3. Обсуди нормальные, ошибочные и граничные сценарии; роли/RBAC/tenant, данные, интеграции, совместимость, миграцию, выпуск/откат и приёмку по применимости. Для исследования выясни вопросы, ограничения усилий и ожидаемый вывод.
4. После исследования проведи следующий раунд вопросов о найденных ограничениях. Собирай максимум полезной информации небольшими тематическими группами. Не заставляй пользователя отвечать на то, что можно доказать кодом; не повторяй решённое. Обязательные ответы нельзя заменять таймаутом или молчанием. Независимые read-only исследования продолжаются.

## Альтернативы и решения

Ищи более подходящие решения, даже не названные пользователем. Если есть содержательные альтернативы, сравни ценность, сложность, SP, риски, поддержку и совместимость; включи меньший полезный объём или использование существующего решения, когда они уместны. Дай рекомендацию и её основания. Не придумывай альтернативы ради количества.

Разделяй факты, гипотезы, предложения и решения пользователя. Расширение результата/объёма не включай молча. Выявленное противоречие текущей бизнес-логике, архитектуре или существенная проблема → покажи evidence, последствия, варианты и рекомендуемое решение; явный human approval требуется ДО зависимой реализации. Запрос «реализуй задачу» не одобряет ещё не предъявленный конфликт.

`DecisionLog`: question ID, решение/открытый вопрос, затронутые задачи, evidence refs, выбранный вариант, risk IDs, plan/acceptance revision и ссылка на явное решение пользователя. Храни краткое очищенное резюме, не raw prompts/переписку. Изменившиеся scope, acceptance или риск инвалидируют соответствующее решение и зависимые планы; разрешение не переносится на другой риск/задачу.

## Готовая постановка / план

Для каждой задачи: цель и пользовательская ценность; текущая реализация и оставшийся объём; in/out scope; сценарии; проверяемые AC; выбранное решение и альтернативы; проекты/репозитории; зависимости (что именно требуется); порядок изменений; тесты и delivery evidence; оценка SP с основаниями; открытые вопросы. Для бага добавь expected/observed, reproduction и RCA перед исправлением.

Эпик дополнительно содержит сквозные сценарии, outcome → task mapping, отдельный план КАЖДОЙ задачи, граф зависимостей без циклов, внешние blockers, порядок контрактов/миграций/выпусков, минимальный полезный объём и общую приёмку. Не заменяй планы задач одним списком названий. Отмена карточки не выполняет её требование; изменение состава согласуется.

Readiness: material questions закрыты, риски явно согласованы, AC проверяемы, repository mapping доказан, dependencies понятны, план и SP актуальны. Не создавай «готовые» карточки с выдуманными ответами. По явному запросу допустим backlog draft с открытыми вопросами, но он не ready for development. При создании используй отдельного [оценщика SP](agents/effort-estimator.md) и независимого Backlog Reviewer; при реализации — оценщика при отсутствии/изменении оценки и независимые route gates.
